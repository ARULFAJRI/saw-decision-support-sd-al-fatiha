# App Flow Document for Decision Support System

## Onboarding and Sign-In/Sign-Up
A new user begins by navigating to the application’s landing page in their browser. The landing page presents a welcome banner and a clear button labeled “Sign In.” If the user does not yet have credentials, they can click a secondary link titled “Create Account” to open the sign-up form. The sign-up form asks for an email address, a password, and a confirmation of that password. When the user submits the form, the application validates that the passwords match and the email has a valid format. A successful submission writes the new user’s details into LocalStorage, assigns the default role of Guru, and then automatically signs the user in. Users who already have an account enter their email and password on the sign-in form. Upon submission, the client-side `useAuth` hook checks LocalStorage for matching credentials, sets a session object in LocalStorage, and redirects the user to the main dashboard. If a user forgets their password, they click the “Forgot Password” link on the sign-in page. This link opens a form where the user enters their email. The system checks LocalStorage for a matching account and then displays a message indicating that a password reset link has been sent. Since this is a client-side implementation, the message explains that the user should contact an administrator to complete the reset. Signing out is available from the user’s profile menu in the header. When the user chooses “Sign Out,” the session data is cleared from LocalStorage, and the user returns to the landing page.

## Main Dashboard or Home Page
After a successful sign-in, the application navigates to the main dashboard. On the left side of the screen is a vertical navigation sidebar with links labeled Dashboard, Student Management, Criteria Management, Evaluation, Reports, and Settings. The top of the screen features a site header that shows the user’s name, a theme toggle button for light or dark mode, and a profile dropdown menu. The center of the dashboard displays four summary cards: the total number of students, the number of criteria, the number of evaluations completed, and the number of reports generated. Each card is clickable, allowing the user to jump directly into the corresponding core module. From any part of the application, the sidebar remains visible for easy navigation. Clicking one of its links transitions smoothly to that feature’s page without a full browser reload, thanks to React Router.

## Detailed Feature Flows and Page Transitions
When the user clicks Student Management, they arrive at a page containing a searchable data table of all students. Above the table, there is an “Add Student” button. Clicking this button opens a form to enter student information such as name, ID number, and class. Once the user fills the form and clicks “Save,” the form data passes to the `services/storage` module, which updates LocalStorage. The page then returns to the updated table view showing the new student. To edit an existing student, the user clicks the edit icon in the student’s table row. This action displays the same form prefilled with the student’s details. After editing and saving, the table updates in place. To delete a student, the user clicks the delete icon and confirms the action in a modal dialog. The criterion management flow is identical to students but operates on the list of criteria objects. Each criterion record holds a name, weight, and type. Editing or deleting follows the same model of inline icons and modal confirmations. In the Evaluation module, the user first selects a criterion set from a dropdown. The application then fetches all students and displays a table with input fields for each criterion score. The user enters numeric scores and clicks “Calculate Rankings.” Behind the scenes, the `utils/saw` function runs normalization, weighted scoring, and ranking. The resulting ranked list appears in a new table below the input form. The user may click “Save Results” to persist the evaluation outcomes to LocalStorage. In the Reports module, the user can view previously saved evaluation results. Clicking on a result expands a detail view. Buttons labeled “Download PDF” and “Download Excel” trigger the jsPDF and XLSX libraries to generate files. After file creation, a download prompt appears in the browser. Every route within these modules is guarded by the `ProtectedRoute` component. If a user without appropriate role data in LocalStorage attempts to access a restricted page, they are automatically redirected to the sign-in page. The Admin role grants access to all pages, while Guru role limits access to Evaluation and Reports only.

## Settings and Account Management
Within the site header’s profile dropdown, the user selects “Profile Settings” to navigate to their account page. There, they see a form showing their email, current role, and an option to change their display name. If the user changes their display name and clicks “Update Profile,” the new value is saved to LocalStorage and immediately reflected in the header. Below the profile form is a theme switcher allowing the user to choose between light mode and dark mode. Toggling the theme updates the `next-themes` setting and persists the user’s preference in LocalStorage. If a future release introduces a subscription or billing feature, a separate tab labeled “Subscription” would appear on this page, showing plan details and payment settings. After updating any settings, the user can click a “Back to Dashboard” link at the bottom of the page to return to the main dashboard.

## Error States and Alternate Paths
If a user submits an empty or invalid sign-in or sign-up form, inline error messages appear next to each invalid field explaining what needs correction. If LocalStorage operations fail—for example, if the storage quota is exceeded—the application displays a modal error message advising the user to clear space or contact support. While navigating between pages, if the application loses power or is refreshed mid-transition, React Router detects the missing session and returns the user to the sign-in page. If the user tries to access a protected route without being authenticated or authorized, the `ProtectedRoute` logic redirects them to sign-in. In the Student or Criteria forms, if required fields are empty, the form validator blocks submission and highlights the missing fields in red. During evaluation calculation, if a nonnumeric value is entered, an inline error appears next to that cell, and the “Calculate Rankings” button is disabled until all inputs are valid.

## Conclusion and Overall App Journey
From initial discovery of the landing page, the user creates an account or signs in with existing credentials. They arrive at a unified dashboard that gives an overview of students, criteria, evaluations, and reports. Using the sidebar and header, they move seamlessly between managing student data, defining evaluation criteria, performing and saving calculations with the SAW algorithm, and exporting results to PDF or Excel. The profile settings page allows them to update personal details and switch themes, and the sign-out option returns them to the landing page. Along the way, clear validations, protected routes based on role, and error handling ensure that the user’s journey from sign-up to daily usage remains smooth and predictable.
